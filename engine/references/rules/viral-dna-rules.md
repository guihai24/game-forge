# 爆款基因自审（第二层 precheck 规则）

> 来源：2026-11-13 对爆款小游戏的第一性原理分析（Flappy Bird、围住神经猫、跳一跳、合成大西瓜、羊了个羊等）+ 宏观/情绪趋势分析。
> 用途：与 `channel-rules.md`（合规自审，答"能不能上架"）并列的第二层。这一层答"值不值得上架"——
> 流水线确认的真正瓶颈是"值不值得上架"和"有没有人玩"，不是"做出来"也不是"上得去"。
> 状态：2026-11-13 已落盘；**2026-11-14 已整合进 precheck**。
> 实现：Gate 1 = `scripts/viral-dna-lib.mjs` 的 `scoreBrief()`；Gate 2 = `scripts/viral-probe.mjs`。
> §六的三项决策当前按文件里的默认值执行（WARN-only / Gate 2 自动跑 / 不拆文档），等用户改主意再调。

## 核心公式

**爆火 = 获客摩擦≈0 × 多巴胺回路成立 × 传播系数>1**（三个变量同时成立，缺一个就不爆）

六条底层原理：
1. 争夺的是注意力回报率：单位时间情绪回报 / 认知成本；对手是短视频、朋友圈、发呆，不是别的游戏。
2. 四种摩擦归零：下载、学习、付费、社交摩擦。
3. 多巴胺回路：即时反馈（<1 秒）+ 可变奖励（随机性）+ 近失效应（"差一点就过了"）+ 蔡格尼克效应（未完成的事一直惦记）。
4. 社交即分发：R0 = 分享率 × 接收方转化率，分享须内嵌进机制，不是角落按钮。
5. 话题性：游戏是谈资生成器——挫败感、争议本身就是传播燃料。
6. 成本结构：单次试错成本趋近于零时，正确策略是批量生产带正确基因的试验品（2014 年 9G 数据：约 100 款出 1 款现象级）。

诚实边界：概率不可能是 100%。这一层提高命中概率，不保证某一款爆。只做"基因筛查"，不做"爆款预测"。

## 判定等级

等级定义与 `channel-rules.md` 一致。本层设计决策：病毒基因项只到 WARN，不设 BLOCK——
"可能爆"无法被证明，BLOCK 会把批量试错堵死。是否接受这个设计，见 §六决策 1。

| 等级 | 含义 | 本层行为 |
|---|---|---|
| **WARN** | 基因缺失，有较大概率跑不起来，需要人判断 | 提示并说明理由，允许继续 |
| **INFO** | 需要注意但不影响基因评分 | 仅提示 |
| **BLOCK** | 本层不设（VD-09 复用合规层已有规则，见 Gate 2） | — |

## 一、三类分析（为什么分三层）

### A. 人为可以控制的 → 编码进生成模板 + 自审规则 + 看板决策

- 摩擦：即点即玩、5 秒上手、免费、无注册（模板强制，自审检查）。
- 核心循环：即时反馈、可变奖励、近失效应（机制参数）。
- 分享机制内嵌：分享得道具、排行、组队（功能清单）。
- 话题钩子：难度、挫败感、争议点（设计输入）。
- 成本与数量：单款制作成本、批量试错规模（这正是 game-forge 的核心价值）。
- 合规：渠道规则、换皮检测、素材原创性（precheck 已实现）。
- 上线时机选择：踩假期、踩热点窗口（执行决策）。
- 砍 / 留决策：留存、分享率、R0 的测量与判断（看板已在做"该砍了"）。

### B. 需要更深层次分析、多维度数据调研才能判断的 → 变成"验证环节"，用数据回答

- 情绪势能：哪个情绪主题正在起势（发疯、解压、治愈）——需持续监测热搜、热榜、搜索词、梗的扩散速度。
- 玩法–情绪匹配度：某种玩法是否真命中某种情绪——只能靠小规模验证回答（TapTap / H5 快速验证环节的意义）。
- 目标人群画像：A 群（待业青年）与 B 群（被 PUA 的打工人）的需求差异——需用户调研和社群观察。
- 渠道红利窗口：哪个渠道现在对哪类游戏友好——持续跟踪审核政策和推荐算法变化。
- 竞品饱和度：某个细分玩法是否已经拥挤——需市场扫描。
- 变现效率：IAA vs IAP、不同渠道 eCPM、留存–收入模型——需真实数据回流。
- 难度曲线最优解：近失效应多强最合适——需 playtest 数据 + 行为数据调参。

### C. 完全不可控的 → 用"批量 + 快速迭代"对冲

- 平台政策突变、宏观经济走向、运气 / 偶然性（大 V 恰好转发、算法恰好推荐）、文化热点突发、
  竞争对手动作、注意力总量竞争（短视频、直播）。
- 对冲方式：单款不可控，但组合的命中概率可控。

### 单局时长分段（2026-11-14 修正）

早期版本统一要求 180–300s，**这个数字没有出处**：Flappy Bird、跳一跳、羊了个羊都是秒级到 1 分钟，
爆款形态是"短局 + 秒重开 + 多局"，不是"一局 3 分钟"。现在按品类分段：

| 节奏 | 品类线索（加权关键词） | 合理区间 |
|---|---|---|
| `twitch` 秒级/短局 | flappy/runner/reflex/tap-game(3) · dodge/jump/dash/click(2) · 躲避/跳跃/反应/点击(2) | 10–90s |
| `midcore` 1–3 分钟 | collect(3) · arcade(2) · collect-and(2) · 收集(2) | 60–180s |
| `strategy` 3–8 分钟 | merge/match3(3) · puzzle/tycoon/tower-defense/idle/sim/strategy/rpg/card(3) · 消除/合成/三消/塔防/经营/放置/策略/卡牌(3) | 180–480s |

判不出来（genre 认不出、brief 没写 `pace`）就**不判**，输出"品类未识别，未判区间"，不当成未达。
brief 里可以显式写 `pace` 覆盖推断。

**复合品类按加权总分定档，不按正则顺序。** 早期实现是三条正则依次 try，先命中的赢：
`collect-and-dodge` 里 `dodge` 属于 twitch、`collect` 属于 midcore，谁在前谁说了算——
这是代码行号在冒充品类判断，一款 100 秒的 collect-and-dodge 会因为正则顺序被判失败。
现在改成表驱动打分：两个档都命中时比总分（collect-and-dodge → midcore 5 : twitch 2）。
`paceDetail()` 会返回每个档的分数和命中的词根，结论可追溯。

### 判分输入不只是 brief

Gate 1 的输入是 `brief` + `.forge/state.json` 台账里的已知事实。brief 漏填 `offline` 但台账记着
`offline: true`，VD-07 应当通过——**已知事实比漏填的字段可信**。

### 静态判定与实测冲突时，实测优先

Gate 1 是"从 brief 文字推断"，Gate 2 是"对产物实测"。brief 没写反馈不代表游戏没反馈。
同一件事两边结论不一致时，以 Gate 2 为准，并在输出里标"实测推翻静态判定"。
映射关系：`VD-03↔VD-03b`、`VD-02↔VD-02b`、`VD-05↔VD-05b`、`VD-07↔VD-07b`。
实现见 `viral-dna-lib.mjs` 的 `reconcileGates()`。

### 砍线口径

**"8 条里缺 2 条以上"指的是能自动判定的项。** VD-04、VD-06 是人工确认项，默认不过；
品类未识别时 VD-02 也是"未判"。这三类都不计入砍线，否则每一款都会被判死。
实现里分别记作 `autoFailed` / `humanCount` / `unmeasuredCount`。

### VD-08 的负向依据同样触发砍线（2026-11-14 补充）

早期实现只检查 `trend_evidence` 是否 ≥10 字。这是错的：写
「本品类当前无窗口期」也够长，但它恰恰说明不该做——只看长度会把**最该砍的结论
判成通过**。

现在的判定：
- **没写** → 项不通过（你还没想过这件事）
- **写了，正向** → 项通过，不额外触发砍线
- **写了，负向**（含「无窗口期 / 已饱和 / 不占势 / 未进榜」等）→ 项算通过（你确实做了判断），
  但置 `negativeTrend`，**直接触发 `suggest-drop`**，不依赖"缺 2 条"的计数

理由：证据说没势，比缺两条基因更硬。缺基因是"可能做不好"，负向趋势是"现在不该做"。

样例见 `references/research/2026-11-14-viral-window.md`：2026-10 微信小游戏畅销榜 Top10
中 SLG 3 席、模拟经营与合并消除各 2 席，**收集躲避类无一进榜**——两款游戏的 trend_evidence
据此写的是负向结论，因此基因分补到 5/8 仍判 `suggest-drop`。这是正确结果，不是 bug。

## 三、Gate 2：提交前建成游戏验证（断言验证，不采信生成器的自述）

**月夜狐灯的教训**：brief 称"AI 美术已替换主角"，实测 game.js 与 5 个素材 MD5 全相同，命中 TapTap 1.4.1 BLOCK。
同理，"玩法已实现分享机制"也不能采信，必须对产物断言。

| ID | 规则 | 等级 | 机器可判 | 断言方式 |
|---|---|---|---|---|
| `VD-05b` | 代码中存在分享 API 调用 | WARN | ✅ 代码 grep | 匹配 `navigator.share` / `wx.shareAppMessage` / `onShareTimeline` / `leaderboard` 等 |
| `VD-03b` | 操作到反馈延迟 <1 秒 | WARN | ✅ playtest 实测 | 操作后任意可观测状态字段发生变化的时间 |
| `VD-03c` | 失败后重开 <2 秒 | WARN | ✅ playtest 实测 | 结束态 → 点击 → 回到 playing 的耗时 |
| `VD-02b` | 单局时长落在本品类区间（见 §二分段表） | WARN | ✅ playtest 实测 | 读运行时倒计时字段，与代码声明交叉核对 |
| `VD-07b` | 冷启动点开到可操作 ≤3 秒 | WARN | ✅ playtest 实测 | 页面导航 → `__gameState` 可读 |
| `VD-09` | 素材与代码去重：与已上架游戏的哈希比对 | BLOCK | ✅ 哈希比对 | 复用合规层 `identical-code` / `same-assets` |
| `VD-06b` | 文案中存在可传播的钩子（战绩 / 省份排行 / 难度争议点至少其一） | INFO | ⚠️ 文案检查 | 文本扫描 |

> **VD-09 的实现方式**：不另写一套哈希比对，直接把合规层的 `identical-code` / `same-assets` / `template-app`
> 三条结果映射成 VD-09 输出（`precheck.mjs` 里做映射）。这是本层唯一的 BLOCK——
> 因为它不是"可能不爆"的预测，而是"换皮必被封"的确定事实，判定依据和合规层完全同一套。

### 三态：达标 / 未达 / 未测

Gate 2 的每一项有三种结果，**不能混为一谈**：

| 结果 | 含义 | 是否计入"未达" |
|---|---|---|
| `ok: true` | 测到了，达标 | 否 |
| `ok: false` | 测到了，不达标 | **是** |
| `ok: null` | 没能力测（品类不支持 / 单局太长没等完 / 状态里没有可观测字段） | 否，单独统计 |

早期版本把"没测到"也算成"未达"，导致换一个没有 `hero` 字段的品类（三消、点击类）会凭空多出
三项失败。现在 `viral-probe.mjs` 用通用的状态变化检测（任意字段变化都算反馈），测不到就报 `?`。

### 各探针的能力边界（别把"测不到"当成"没有"）

- **VD-05b**：只统计分享 API 出现次数，**没有做可达性分析**。"分享入口在核心循环可达路径上"无法靠正则判断。
  这一项只回答"有没有接分享"，不回答"是不是内嵌在玩法里"——后者进人工清单。
- **VD-07b**：测的是 `file://` 本地加载，不含网络传输。它反映"游戏自身初始化多快"，
  不是真实首次打开体验（真实冷启动还要加渠道包下载时间，那部分平台测不了）。
- **VD-03c**：需要等一局自然结束，单局超过 20 秒就放弃，报"未测"。
- **VD-03b**：依赖游戏暴露 `window.__gameState()`。不暴露就整项测不了（`probed: false`）。
  检测方式是**基线差分**：先不输入采样 5 次，记录每个字段的自主变化速率；再输入，
  只有变化速率显著超过基线（3 倍以上）的字段才算"输入造成的反馈"。
  早期版本把"任意字段变化"当反馈，但动态游戏里敌人一直在动、计时器一直在走——
  实测 dawn-otter 在不输入的情况下 5/5 次采样都变，那些读数反映的是自主运动的相位，
  不是输入生效时间。改后归因到具体字段（`hero.x`、`score`）。
  输入方式覆盖拖拽 / 点击 / 按键三种，因为只试拖拽的话点击类游戏永远测不到。

Gate 2 输出一份"值不值得上架"摘要，供看板砍 / 留决策用，不是放行关卡。

## 四、"势"的输入层（不写进规则，只作 brief 输入）

情绪主题会过期（谷子经济 2024 年已 1689 亿、品牌都下场了，再进就是接盘），所以主题不硬编码进规则，
只作为每次立项时 brief 的输入字段：`emotion_theme` + `trend_evidence`。

- 当前与用户资产最匹配的情绪主题：职场发泄、解压 / 发泄类小游戏（砸键盘、怼领导模拟器、摸鱼放置、治愈整理）。
- 持续监测信号（势刚起时进，势已满时不追）：热搜 / 热榜情绪词、新梗出现与扩散速度、情绪消费品类销量异动、平台搜索词暴涨。

## 无法机器判断的怎么办

`VD-04`（近失设计）、`VD-06`（话题钩子）机器给不出确定结论。做法与合规层一致：

- 不假装能判，输出「需人工确认」+ 具体要确认什么
- 让 agent 在需求梳理时主动问用户
- 提交前生成一份「自查清单」，人工逐项打勾
