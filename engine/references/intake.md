# 需求梳理

用户开口往往只有一句"做个 XXX 的游戏"。直接开工的结果通常是：做完了发现渠道不对、
或者验收标准根本不是他想要的。**先用三层问题补齐，再动手。**

不要一次抛十个问题。**按层问，能推断的就不问。**

## 第一层：渠道（最优先，决定整条路径）

> 这个游戏你想发到哪儿？微信小游戏，还是网页？

| 回答 | `target` | 后续 |
|------|----------|------|
| 微信小游戏 / 小程序 / 要能在微信里玩 | `wechat` | 走小游戏工程 + 开发者工具 |
| 网页 / 浏览器里打开 / 发给朋友点链接 | `web` | 暂缓（见 `web.md`） |
| 都想要 | 先做 `wechat` | 网页那条后续补，代码可复用 |

为什么放第一位：它决定产物格式、验证方式、发布手段**完全不同**。玩法再怎么变，
渠道选错就是白做。

补充问题（按需，不要全问）：

- **要在手机上玩还是电脑上玩？** → 决定 `orientation`（`portrait` / `landscape`）
- **是自己玩、内测，还是要正式上线？** → 决定验收严格程度、要不要真机验证

## 第二层：玩法（决定这是什么游戏）

> 玩起来是什么样的？

**这一层不能靠问，要靠玩。**

用户不懂游戏术语，也无法从"点击猛砸 / 60 秒躲避"这类文字里想象出手感。
2026-11-15 实测：问「玩起来是什么手感」，用户回「需要讨论一下看看定位是什么」——
**没选**。流程却按推荐项（躲避）继续往下做，做完 58 步、几十万 token 之后，
用户才说「整个产品形态就有问题」。

所以流程是：

```
1. 听题材（用户的场景、情绪、想吐槽的东西）
2. agent 用 engine/references/genres/README.md 挑 3 个玩法，
   配上这个题材的场景化描述
3. 生成 3 个能玩的原型（各 30–60 秒，无美术）：
       node engine/scripts/prototype.mjs --genre <类型> --title "<标题>" --out <目录>
4. 用户挨个玩，只说「这个对 / 不对」
5. 用户选定之后才写 brief、进正式开发
```

**不要问用户**：
- ✗ "你想选哪个 genre？"
- ✗ "核心循环是什么？"
- ✗ 任何包含 ACT / PUZZLE / match-3 这类词的选项

**要问的**：
- ✓ "我做了三个能玩的，各 30 秒，你试试哪个感觉对"

玩法定了之后，再补这两个（这时用户已经有一个具体的东西可以参照）：
- 一局多长？→ `rules.duration`
- 主角是谁、障碍是什么？→ 美术槽位

### 玩法与节奏是两个维度，别混

`genre`（玩家反复做什么）和 `pace`（一局多长）是正交的。
"休闲"不是玩法，是节奏——消消乐是「解谜 + 休闲」，五子棋是「棋牌 + 休闲」。
把两者混成一个字段，正是之前所有游戏最后都变成同一个模板的原因。

### 生成原型之前先查重

`node engine/scripts/prototype.mjs --list` 看现有类型。
如果工作区里已经有同类型的游戏，**换一个类型**——判断依据是玩法，不是代码相似度。

## 第二层半：值不值得做（爆款基因）

> 玩法定了之后问。**这一层决定要不要做，不是怎么做。**
>
> 规则来自 `rules/viral-dna-rules.md`。核心判断：爆火 = 获客摩擦≈0 × 多巴胺回路成立 × 传播系数>1，
> 三个变量缺一个就爆不了。这里问的是能不能拿到这三个变量。

**只问 brief 里填不出来、又必须由用户决定的三件事**，其余机器能判的就别问：

| 该问的 | 落到 |
|---|---|
| 这游戏分享给朋友时，他是从哪来的？（能直接开玩/要下载/要注册） | `offline`，决定 VD-07 零摩擦 |
| 有没有任何付费点？（内购/虚拟支付/解锁） | `iap`，有内购必须版号 |
| 分享是玩法的一部分，还是角落里一个按钮？ | `share`，`VD-05` 分享即机制 |
| 玩家失败时会觉得「差点就过了」还是「这游戏不公平」？ | `VD-04` 人工项，要用户确认 |
| 玩完之后他会跟朋友说什么？ | `VD-06` 人工项，要用户确认 |
| 现在为什么是这个题材？看到什么信号了？ | `emotion_theme` + `trend_evidence` |
| 这个势是**正**的还是**负**的？（有窗口期 / 没有） | `trend_direction`，填 positive 或 negative |

最后一条**不能跳过**。情绪主题会过期——谷子经济 2024 年已经 1688 亿、品牌都下场了，再进就是接盘。
没有"势"的依据就不要立项，而不是做完再说。

**问完立刻跑一次 Gate 1**，别等到写完代码：

```bash
node scripts/precheck.mjs --brief <游戏目录>/game.brief.json --channel <target>
```

`viral-dna score` 低于 6/8 要跟用户说清楚缺什么；缺 2 条以上**建议别做**（不阻断，但要明说）。

## 第三层：交付（决定验收标准）

> 这次是想先看看效果，还是要能发给别人玩？

| 回答 | 验收标准 | 命令 |
|------|----------|------|
| 先看看 | `mustReachPhase: ["playing"]`，fps ≥ 45 | `--preview` |
| 要给别人玩 | 加上 `mustScore`（证明核心循环真的能得分） | `--preview` + 真机 |
| 要上线 | 需要正式 AppID、真机验证、内容审查 | `--upload`（**当前未验证**） |

要不要 AI 美术也在这里问：

- 不要 → 用代码绘制的占位角色，先跑通流程
- 要 → 提醒按张计费（medium 档实测约 $0.05/张），且**先把游戏跑通再换美术**

## 收尾：落成 brief.json

```bash
node scripts/brief.mjs init --out <游戏目录>/game.brief.json \
  --title 月夜狐灯 --genre collect-and-dodge --target wechat \
  --appid wx... --orientation landscape \
  --emotion-theme 解压 --trend-evidence "微博焦虑词频三周上涨，摸鱼类搜索翻倍"
node scripts/brief.mjs check --file <游戏目录>/game.brief.json
node scripts/precheck.mjs --brief <游戏目录>/game.brief.json --channel wechat
```

必填：`title`、`genre`、`target`、`acceptance.mustReachPhase`、`acceptance.minFps`。
`channel.appid` 为空只是警告（只能跑模拟器，不能预览上传）。

**爆款基因相关字段**（写进 brief，Gate 1 会读）：

| 字段 | 说明 |
|---|---|
| `offline` | `true` = 单机免注册。没写会被判 VD-07 不过（除非台账里记着） |
| `iap` | `true` = 有内购。个人主体拿不到版号，这一项是硬约束 |
| `share` | 分享机制，如 `{"kind":"leaderboard"}`。空则 VD-05 不过 |
| `pace` | 节奏档 `twitch` / `midcore` / `strategy`，留空则从 genre 推断 |
| `emotion_theme` | 情绪主题（解压/职场发泄/治愈…）。会过期，所以只作输入 |
| `trend_evidence` | 凭什么现在是这个题材的窗口期。空则 VD-08 不过 |
| `trend_direction` | `positive` / `negative`。**必须显式标**，机器不猜。标 negative 会直接触发砍线建议 |

## 反例：什么情况下别问

- 用户已经说清"微信小游戏" → 渠道不用再问
- 用户直接给了玩法细节（"60 秒内收集 20 个灯笼"）→ 玩法层直接落 `rules`
- 用户说"你看着办" → **按最熟的路径做**（wechat + collector + landscape），做完再给选项

判断标准：**问的每一个问题，都要能改变后面某一步的做法。** 改变不了的就是多余。
