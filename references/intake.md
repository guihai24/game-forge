# 需求梳理

用户开口往往只有一句"做个 XXX 的游戏"。直接开工的结果通常是：做完了发现渠道不对、
或者验收标准根本不是他想要的。**先用三层问题补齐，再动手。**

不要一次抛十个问题。**按层问，能推断的就不问。**

## 第一层：渠道（最优先，决定整条路径）

> 这个游戏你想发到哪儿？微信小游戏，还是网页？

| 回答 | `target` | 后续 |
|------|----------|------|
| 微信小游戏 / 小程序 / 要能在微信里玩 | `wechat` | 走小游戏工程 + 开发者工具 |
| 网页 / 浏览器里打开 / 发给朋友点链接 | `web` | 暂缓（见 `web.md`） |
| 都想要 | 先做 `wechat` | 网页那条后续补，代码可复用 |

为什么放第一位：它决定产物格式、验证方式、发布手段**完全不同**。玩法再怎么变，
渠道选错就是白做。

补充问题（按需，不要全问）：

- **要在手机上玩还是电脑上玩？** → 决定 `orientation`（`portrait` / `landscape`）
- **是自己玩、内测，还是要正式上线？** → 决定验收严格程度、要不要真机验证

## 第二层：玩法（决定模板与规则）

> 玩起来是什么样的？

不要问"你想用什么引擎"这类实现问题，用户不关心。问**体验**：

| 该问的 | 映射到 |
|--------|--------|
| 玩家在干什么？收集？躲避？消除？对战？ | `genre`，选模板 |
| 多久一局？还是一关一关过？ | `rules.duration` 或关卡制 |
| 怎么算赢？怎么算输？ | `rules.goal` / `hearts` / `acceptance.mustReachPhase` |
| 主角是谁？敌人/障碍是什么？要收集什么？ | 美术槽位 |

**收集躲避类**（collector 模板）是这个流水线最熟的品类，一次成型的概率最高。
其它品类（三消、塔防、跑酷、卡牌）能做，但要提醒：转换器的兼容性检查会更常拦人。

## 第三层：交付（决定验收标准）

> 这次是想先看看效果，还是要能发给别人玩？

| 回答 | 验收标准 | 命令 |
|------|----------|------|
| 先看看 | `mustReachPhase: ["playing"]`，fps ≥ 45 | `--preview` |
| 要给别人玩 | 加上 `mustScore`（证明核心循环真的能得分） | `--preview` + 真机 |
| 要上线 | 需要正式 AppID、真机验证、内容审查 | `--upload`（**当前未验证**） |

要不要 AI 美术也在这里问：

- 不要 → 用代码绘制的占位角色，先跑通流程
- 要 → 提醒按张计费（medium 档实测约 $0.05/张），且**先把游戏跑通再换美术**

## 收尾：落成 brief.json

```bash
node scripts/brief.mjs init --out <游戏目录>/game.brief.json \
  --title 月夜狐灯 --genre collect-and-dodge --target wechat \
  --appid wx... --orientation landscape
node scripts/brief.mjs check --file <游戏目录>/game.brief.json
```

必填：`title`、`genre`、`target`、`acceptance.mustReachPhase`、`acceptance.minFps`。
`channel.appid` 为空只是警告（只能跑模拟器，不能预览上传）。

## 反例：什么情况下别问

- 用户已经说清"微信小游戏" → 渠道不用再问
- 用户直接给了玩法细节（"60 秒内收集 20 个灯笼"）→ 玩法层直接落 `rules`
- 用户说"你看着办" → **按最熟的路径做**（wechat + collector + landscape），做完再给选项

判断标准：**问的每一个问题，都要能改变后面某一步的做法。** 改变不了的就是多余。
